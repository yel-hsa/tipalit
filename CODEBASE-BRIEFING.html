01

What it is

TIPalit is a mobile-first C2C marketplace for students at the Technological Institute of the Philippines (Manila and QC campuses). Students sell used academic goods — textbooks, calculators, uniforms, lab gear — to other verified TIP students, handing off in person at admin-approved campus spots.

The thesis, from PRD.pdf §2.3: gated @tip.edu.ph identity, zero shipping, and curriculum-aligned discovery (subject code, department, campus) beat cluttered Facebook buy-and-sell posts, scam-prone public marketplaces, and three-to-five-day Shopee shipping. Money comes from sponsor banners and an affiliate “Student Perks” list, not from students.

Everyone is both buyer and seller. There is no separate seller account. The app partitions the market by campus: each user sees only their campus's listings, spots, and new posts.

The PRD is a course deliverable (GEE003 Entrepreneurial Mindset, BS IT 2026), so it mixes lean-canvas material with engineering requirements. Where docs and code disagree, the code wins. Three known drifts: shipped conditions are New / Like New / Good / Fair, not the PRD's wording; auth shipped as Google-only rather than email + verification; and price filter, condition filter, payment-method notes, and paid boosts are planned but absent.

The four journeys

  • Onboard — intro carousel → Continue with Google → pick account → profile (name, campus, program, year) → safety pledge → feed.
  • Buy — feed → listing → Message Seller → propose spot / day / time → seller accepts → meet → Mark done → rate 1–5.
  • Sell — Sell tab → form → detail with Edit / Mark sold / available / Delete.
  • Moderate — report → admin queue → remove listing or suspend member or dismiss with a note → audit entry.
02

How to run it

Node 22 + pnpm 10.34.3 per .mise.toml. Only pnpm-lock.yaml exists, so use corepack pnpm.

corepack pnpm install
VITE_DATA_ADAPTER=mock corepack pnpm dev   # http://localhost:8443

The adapter switch

src/services/index.ts picks the backend once at module load. VITE_DATA_ADAPTER=firebase|mock wins outright. Otherwise Firebase is used if both VITE_FIREBASE_API_KEY and VITE_FIREBASE_PROJECT_ID are set; otherwise mock. There is no runtime toggle. Mock state lives in localStorage under tipalit.v2.*.

The one trap that matters first: if your .env has real Firebase keys, the dev server writes to live Firestore without asking. Set VITE_DATA_ADAPTER=mock explicitly to stay local. README.md:72 claims unknown adapter values log a warning; the code does no such thing.

Other operational facts

  • Vite binds 0.0.0.0:${PORT:-8443} with strictPort: true — a busy port is a hard failure, not a fallback.
  • Reviewer / demo mode: ?reviewer=1, VITE_REVIEWER_MODE=true, or seven taps on the version line in Profile. Mock-only; enables demo tools in any build.
  • No typecheck or test in the build. Run corepack pnpm exec tsc --noEmit yourself.
  • firebase.json has no hosting block, so firebase deploy --only hosting fails. Frontend ships via .figma/make/deploy to Figma Make hosting.
  • Not a git repository. AGENTS.md is a stale scaffold doc that says the dev server is already running and lists seven files.

06

Data and backend

The seam

src/services/index.ts exports a single services object. Screens import nothing else from data. Errors are a ServiceError with codes: network, storage, not_found, unauthenticated, forbidden, invalid.

Mock — a full offline backend

600 ms simulated latency (2 s under slow network), simulated seller typing and replies, meetups auto-accept or decline after 1.5 s, one-shot failure flags for load and publish, and a React-bridged fake Google account chooser. Only the mock exposes services.demo; all reviewer tooling keys off it.

Firestore collections

users_profile · listings · chats (+ messages subcollection) · reviews · reports · promotions · settings (singleton meetup_spots) · promotion_clicks · audit_log · analytics_events

Security model

Every rule requires isTipStudent(): email matches @tip.edu.ph and email_verified == true. isAdmin() is the token email osa.admin@tip.edu.ph or users_profile/{uid}.role == 'admin'. Owners cannot write role or status, so a self-promotion via profile edit is closed. Owner listing updates cannot touch report_count and cannot set status 'hidden'.

Cloud Functions

  • onReportCreated — increments the listing's report_count, flips it to hidden at 5 reports.
  • onReviewWritten — maintains average_rating and total_reviews transactionally.
  • resolveReport — callable admin action that closes sibling reports and writes an audit_log entry.

Storage

item_photos/{uid}/{listingId}/{fileName}, readable by any TIP student, writable only by the owner, jpeg / png / webp under 5 MB. promo_assets/ is admin-write.

07

The things that will bite you

  1. The client never calls resolveReport. correctness
    Firebase admin resolves reports with direct Firestore writes, bypassing the sibling cascade and the Function's hidden status. The client sets listings to 'removed' instead. Only 'hidden' is blocked for sellers, so a seller can revive a removed listing. src/services/firebase/admin.ts
  2. Firebase mode fabricates admin data. correctness
    The admin service falls back to seeded reports and audit entries when Firestore is empty or errors, so a demo on live data can show fake reports. It also returns activeListings: 0, openReports: 0 for every member. firebase/admin.ts:228-229
  3. Firebase analytics queries the wrong collection. correctness
    It reads 'users'; profiles live in 'users_profile', so the Members tile is always zero. The same function also fetches all listings, reports, and reviews just to count them. src/services/firebase/analytics.ts:23
  4. Firebase chat swallows errors. resilience
    respondToMeetup, completeMeetup, and rate log and return void, so App's rollback and error toast never fire. openThread returns a synthetic thread ID when the write fails, and the next message dies against a nonexistent doc. firebase/chat.ts:253-331
  5. Live listings sort on a field never written. correctness
    Create writes created_at and server_timestamp; toListing and both sort paths read data.createdAt. Every live listing ties on the same fallback timestamp. firebase/listings.ts:61,81,92,144-145
  6. Profile save is rejected by the rules. blocks live mode
    The client writes program, which is absent from the allowed update keys in firestore.rules:57-60. Editing an existing profile fails in Firebase mode.
  7. Firebase onboarding can skip profile setup. latent
    firebase/auth.ts:150-171 creates a profile with campus 'qc' and department 'General', which makes isProfileComplete() true immediately. Not exercised in tests; uncertain whether anything clears those placeholders.
  8. Live feed query and indexes disagree. infra
    The feed uses status not-in ['hidden','removed'] plus campus equality; firestore.indexes.json declares campus+status and campus+category/department orderings the client never issues.
  9. Audit log field mismatch. cosmetic
    The Function writes actor_name; AdminScreen.tsx:263 reads entry.actorName. Function-written rows show a blank actor.
  10. The mock is more complete than production. testing
    No hidden or removed states, no report auto-hide, no parity with Firebase's suspension filtering. Demo success does not imply live success.
  11. Accessibility holes in dialogs. a11y
    useDialogFocus traps focus only inside the dialog body. ReportModal lacks aria-modal and Escape. BottomSheet does not inert the background.
  12. App.tsx races. correctness
    load() guards only four setters. fetchThreads, fetchAdmin, cacheListings, and ensureSellers run uncancelled and can repopulate state after sign-out. Rollback closures capture render-time values.

Two smaller ones: there is no error boundary anywhere in src/main.tsx, and guidelines/Guidelines.md tells you to install @figma/astraui-kit and read guidelines/setup.md — neither exists (the package is @figma/astraui).

08

Open questions

  1. Which backend is authoritative for moderation? Reconcile client-side admin writes, the unused resolveReport, and the split hidden / removed states. Pick one path.
  2. Fix or retire the Firebase fallback-to-seed pattern in admin.ts. It is a credibility risk in any demo on live data.
  3. Fix profiles.save against the rules, and the placeholder 'qc' profile. Both can silently eat a real user's first session.
  4. PRD backlog or dead code? Price filter, condition filter, payment-method note, featured boost, separate Perks tab. None are scheduled outside the PRD.
  5. Ownership invariants. Nothing stops a seller changing seller_id or campus. status: 'reserved' is unreachable from the UI.
  6. Production gates. No typecheck or tests in CI, no error boundary, no Hosting config, default page title and noindex in .figma/make/site.json.
  7. Privacy. Student PII in Firestore, no account deletion, no data export, no logout-all.
